How it builds code

The steps the agent followed, in order. Indented lines run under the line above them.

Family: Structure first. Idea: Plan classes from spec nouns and methods from verbs. Fill linked stubs. What it changes in the search: The map. Fixed before any code.

once:1. Gather the spec and its acceptance tests. Write tests for any untested feature.2. Extract every noun and verb as Noun: -verb lists. Trim to the domain.3. Mark parents as Noun(Parent). Split nouns over 4 verbs. Apply Clean Code names.4. Replace duplicate verbs with references written as verb1(Noun2.verb3).5. Script-check for cycles, dangling references and nouns over 4 verbs. Fix each.6. Scaffold stubs that throw a TODO naming the referenced method. Fill one per prompt.7. Run the tests. Fix one failing test per prompt with the smallest change.8. Lint with no suppressions. Prune unused methods. Diff a regenerated map against the plan.

Once means one agent runs the steps. Repeat per unit means one agent per unit until no unit is open. Throughout means the rule joins every prompt. For up to n starts means separate attempts with the best kept. The harness does means the harness runs the step without an agent. If names the event that starts a stage, and with adds a rule borrowed from another method. Steps are quoted from args.json with their numbers. Tag: verified.

Review scores

A blind reviewer agent scored src/ and test/ from 1, worst, to 5, best, so the scores are unchecked. Reasons are the reviewer's own words, verbatim. This review is superseded by the blind rating of three raters in rating.json, whose medians fill the comparison's principle columns.

Review scores, 11 rows and 4 columns

Alterability. Item: Change Case 1: sow seeds anti-clockwise. Score /5: 5.

Reason: Direction is read in a single place, the isClockwise branch in Display.showBoard, which reuses one row helper for both layouts. Sowing and capture logic need no change for either direction.

Alterability. Item: Change Case 2: 7 houses with 5 seeds. Score /5: 5.

Reason: House count and starting seeds come only from Variant.houseCount and initialSeeds, and the board, rendering and loops scale from that count. Changing or adding a size touches one class.

Code quality principles. Item: 1. Clear Presentation. Score /5: 4.

Reason: Small files with consistent indentation and wrapping make the classes easy to scan. Display mixes board rendering with message output, and Console sits apart from the Prompt subclass that extends it, which blurs where IO lives.

Code quality principles. Item: 2. Explanatory Language. Score /5: 4.

Reason: Names such as sow, endsInOwnStore, captureOpposite and oppositeHouse read like the rules, and the javadoc lines give intent. The Game constructor comment about a coupling limit explains process instead of design, and the literals 6/7 and 4/5 in Variant have no named constants.

Code quality principles. Item: 3. Consistent Code. Score /5: 3.

Reason: houseCount is threaded as a separate argument into Game, Move, Side and Prompt although Variant and Player already know it. IO is wrapped twice, once as the Console for Display and again through Prompt extends Console, so the same concern has two instances.

Code quality principles. Item: 4. Used Content. Score /5: 3.

Reason: Prompt.readChoice only forwards to readHouse, GameOver.announceResult is a public step used once, and Board.houses duplicates the house lists Player already holds. Board.seedsIn and isEmpty only forward to Player.

Code quality principles. Item: 5. Simple Constructs. Score /5: 3.

Reason: Move.capture loops over every house to find whether the last pit is the mover's own house, where a direct check would do. Side.hasMoves accumulates a boolean through the whole loop when an early return is plainer, and Board.nextPit uses indexOf on every seed.

Code quality principles. Item: 6. Minimal Duplication. Score /5: 4.

Reason: The two clockwise and anticlockwise board layouts share one row() helper, and the score and has-moves loops each appear once. The house loops over 1..houseCount repeat across Side, Move and Display, and the two Player constructors repeat the house setup.

Code quality principles. Item: 7. Modular Structure. Score /5: 4.

Reason: Pit, House, Store, Player, Board, Move, Side, Game and GameOver each carry one clear job, and the direction choice stays inside Display. Using inheritance from Console for Prompt and pushing a raw houseCount into many classes adds coupling that a shared Variant or Board would avoid.

Code quality principles. Item: 8. Problem Alignment. Score /5: 5.

Reason: The model uses the domain terms houses, stores, sowing, capture, extra turn and opposite house directly. It also shows that the direction only changes the board layout because the sowing ring stays the same in both variants.

Test quality. Item: Test quality. Score /5: 3.

Reason: Six spec-driven tests with clear names cover quit, extra turn, capture and wrapping past the own store across several variants that the starter examples leave out. Coverage is uneven: there are no unit tests of Move, Board or Side, no empty-house or game-end tests, and anticlockwise 7-5 capture and some variant combinations are missing.
