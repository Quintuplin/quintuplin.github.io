throughout:7. Keep the Book current as the code changes. Log each decision and mark each milestone done.once:1. Write the Anchor Book ANCHORS.md at the clone root from README.md and docs/SPEC.md. It holds the design, each anchor as a claim that must hold about the system, the criterion that verifies it, and the planned chunks of work as milestones.2. Check each anchor against the others and the spec. Log each conflict and the decision taken in the Book.repeat per milestone until none is open:3. Per milestone, turn each of its anchors into tests that check it. Record in the Book which tests verify which anchor. Test names describe behaviour and carry no anchor ids.4. Review scores

A blind reviewer agent scored src/ and test/ from 1, worst, to 5, best, so the scores are unchecked. Reasons are the reviewer's own words, verbatim. This review is superseded by the blind rating of three raters in rating.json, whose medians fill the comparison's principle columns.

Review scores, 11 rows and 4 columns

Alterability. Item: Change Case 1: sow seeds anti-clockwise. Score /5: 5.

Reason: Direction is treated as a mirror of the drawing. One boolean in BoardView picks the row order, and Board and Game have no direction code at all. A change to direction touches one small branch in one class, and it combines freely with any board size.

Alterability. Item: Change Case 2: 7 houses with 5 seeds. Score /5: 5.

Reason: Board size lives in Variant.from as one ternary of house and seed counts. Board, BoardView and Game all derive everything from houseCount, so supporting 7-5 or another size is a one-line change.

Code quality principles. Item: 1. Clear Presentation. Score /5: 5.

Reason: Files are short and consistently indented, with methods ordered from public to private helpers. Line length is controlled and the layout makes related elements easy to see.

Code quality principles. Item: 2. Explanatory Language. Score /5: 4.

Reason: Class Javadocs state each class's intent, and names such as sow, captureAt, hasMoves and toHouse are clear. Some literals stay unexplained: 3 - player is used for the opponent and 2 * houseCount - pit for the opposite pit. The changed play() Javadoc also no longer describes sowing direction.

Code quality principles. Item: 3. Consistent Code. Score /5: 5.

Reason: Players are 1-based and houses 1..n everywhere. The final classes, package-private APIs and test helpers follow one style throughout.

Code quality principles. Item: 4. Used Content. Score /5: 5.

Reason: No dead code. Every method and field is used, and the stub board printing was removed.

Code quality principles. Item: 5. Simple Constructs. Score /5: 4.

Reason: Loops are flat with early returns. The circular pit array and the skip-store loop are compact, but the index arithmetic in captureAt and the own-house range check take some effort to verify.

Code quality principles. Item: 6. Minimal Duplication. Score /5: 4.

Reason: The source has almost no repetition, apart from 3 - player appearing in several places without a named opponent helper. The tests repeat the FULL_GAME move list, a seed-total loop and a board-initialisation assertion across files.

Code quality principles. Item: 7. Modular Structure. Score /5: 5.

Reason: Responsibilities are clearly split. Board holds rules and state with no output, BoardView handles rendering, Game runs the turn loop with IO, Variant handles sizing, and Kalah wires them together. Dependencies are minimal and fields are private.

Code quality principles. Item: 8. Problem Alignment. Score /5: 4.

Reason: Board, house, store, sow and capture follow the domain closely. Modelling clockwise as only a display mirror is valid but implicit, and only the class comments explain it, so a reader looking for sowing direction will not find it in the rules.

Test quality. Item: Test quality. Score /5: 4.

Reason: Tests cover sowing, wrap-around, extra moves, captures, the no-capture case, scoring, all three end results, invalid input, quit, both layouts and both sizes, with a spec file run in each of the four variants. Names are descriptive and cases are independent. Some move scripts were found by search and their expected values are opaque, and fixtures are duplicated.
