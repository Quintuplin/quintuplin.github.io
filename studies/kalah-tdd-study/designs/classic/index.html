Family: Baseline. Idea: Smallest failing test then smallest passing change. What it changes in the search: Nothing. It is the greedy baseline.

once:1. List test scenarios from the requirements before writing code.repeat per feature until none is open:2. Pick the scenario that needs the least new code.3. Write one failing test for it and watch it fail.4. Pass it with the smallest change. Reject assistant diffs that do more.5. Fake a constant if unsure. Generalize once a second example forces it.6. Type the obvious code when sure. Drop back to faking on a surprise red.7. Refactor on green. Add new scenarios to the list. Repeat until empty.

Once means one agent runs the steps. Repeat per unit means one agent per unit until no unit is open. Throughout means the rule joins every prompt. Review scores

A blind reviewer agent scored src/ and test/ from 1, worst, to 5, best, so the scores are unchecked. Reasons are the reviewer's own words, verbatim. This review is superseded by the blind rating of three raters in rating.json, whose medians fill the comparison's principle columns.

Review scores, 11 rows and 4 columns

Alterability. Item: Change Case 1: sow seeds anti-clockwise. Score /5: 4.

Reason: Sowing works in index order for both directions, so the clockwise flag only reaches printBoard. The cost is a set of dense ternaries spread over several lines there instead of one place that decides the layout.

Alterability. Item: Change Case 2: 7 houses with 5 seeds. Score /5: 4.

Reason: The variant sets only two inline ternaries in play(), and every loop and the board width come from the array length. The literal 7/5/6/4 values have no named constants.

Code quality principles. Item: 1. Clear Presentation. Score /5: 3.

Reason: The methods are short and well separated. The indentation mixes tabs and spaces, and the printBoard lines that chain ternaries with substring(1) are hard to read.

Code quality principles. Item: 2. Explanatory Language. Score /5: 3.

Reason: The Javadoc on sow and capture states the intent well and most names are descriptive. Magic literals (7, 5, 6, 4, -1, "q") and the bare 0/1 player indices carry no names, and printBoard has no comment.

Code quality principles. Item: 3. Consistent Code. Score /5: 3.

Reason: The helpers are static except printBoard. java.util.Arrays is fully qualified inline and never imported. Strings are built with += in one place and with a StringBuilder in another.

Code quality principles. Item: 4. Used Content. Score /5: 5.

Reason: Every element is used and no dead code remains from the stub.

Code quality principles. Item: 5. Simple Constructs. Score /5: 3.

Reason: The game loop is plain. The sow loop's index reset to -1 with side flipping and an early return inside nested ifs takes careful reading. printBoard relies on nested conditional expressions.

Code quality principles. Item: 6. Minimal Duplication. Score /5: 4.

Reason: The house and repeat helpers and the shared store strings avoid repetition. The sum over seeds[player] appears twice and the store-format logic is mirrored across rows.

Code quality principles. Item: 7. Modular Structure. Score /5: 3.

Reason: Functions are small and each does one task. Board state is passed around as parallel raw arrays in one class, with no Board or Player abstraction to hold game state apart from IO.

Code quality principles. Item: 8. Problem Alignment. Score /5: 3.

Reason: The sow, capture and printScores names match domain terms. The board as int[2][n] plus stores[2], with players as 0/1, sits closer to implementation than to the game's concepts.

Test quality. Item: Test quality. Score /5: 3.

Reason: The spec-driven tests have clear behaviour names and cover capture, no-capture, extra move, store skip, exact lap and all three game-end outcomes. Variant coverage is uneven: anticlockwise 7-5 gets only a quit test and most rules are pinned for one variant.
