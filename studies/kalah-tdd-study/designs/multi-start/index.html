How it builds code

The steps the agent followed, in order. Indented lines run under the line above them.

Family: Search and validation. Idea: Independent attempts on one locked suite. Score rule fixed first. What it changes in the search: Breadth. Several starts and the best is kept.

once:1. Write the shared acceptance tests and lock them with a hash check in CI.2. Fix budget and score up front. Default is green first then mutation score then fewer lines.3. Pick 2 to 4 start strategies such as noun-verb map, smallest-test TDD or functions first.for up to 3 starts, keep the best:4. Run each attempt on its own branch until green or out of budget.5. At half budget drop any attempt passing under half the leader's tests.once:6. Score the finished attempts. If none is green rank by tests passed.7. Keep the winner. Archive the others with a note on what each taught.

Once means one agent runs the steps. Repeat per unit means one agent per unit until no unit is open. Throughout means the rule joins every prompt. For up to n starts means separate attempts with the best kept. The harness does means the harness runs the step without an agent. If names the event that starts a stage, and with adds a rule borrowed from another method. Steps are quoted from args.json with their numbers. Tag: verified.

Review scores

A blind reviewer agent scored src/ and test/ from 1, worst, to 5, best, so the scores are unchecked. Reasons are the reviewer's own words, verbatim. This review is superseded by the blind rating of three raters in rating.json, whose medians fill the comparison's principle columns.

Review scores, 11 rows and 4 columns

Alterability. Item: Change Case 1: sow seeds anti-clockwise. Score /5: 5.

Reason: Direction lives only in Render.board as two ternaries that mirror the rows. Sowing order is the same in both directions, so the rules need no direction branch at all.

Alterability. Item: Change Case 2: 7 houses with 5 seeds. Score /5: 5.

Reason: One ternary in play picks Rules.init(7,5) or (6,4). Every other size comes from Rules.houses(board), so the rules and rendering adapt without further edits.

Code quality principles. Item: 1. Clear Presentation. Score /5: 4.

Reason: Short functions and a tidy play loop read easily. The index arithmetic in store, pitOf and the opposite formula 2*houses-last is terse and asks the reader to recall the layout comment.

Code quality principles. Item: 2. Explanatory Language. Score /5: 4.

Reason: Names such as sow, capture, nextPit and houseSeeds match the domain, and the class comment documents the board layout. pitOf and the bare 0/1 player ints are a little cryptic.

Code quality principles. Item: 3. Consistent Code. Score /5: 4.

Reason: Static helpers taking (board, player, ...) follow one pattern throughout. Kalah.java mixes tab and space indentation from the starter.

Code quality principles. Item: 4. Used Content. Score /5: 4.

Reason: Nearly everything is used. capture returns a boolean that move ignores, and the main stub is kept as given.

Code quality principles. Item: 5. Simple Constructs. Score /5: 4.

Reason: Plain loops, arrays and ternaries. The recursive nextPit is a slightly clever way to skip the opponent store.

Code quality principles. Item: 6. Minimal Duplication. Score /5: 5.

Reason: Layout arithmetic is centralised in Rules helpers reused by Render and Kalah. Row rendering is shared through row and houses with a direction flag.

Code quality principles. Item: 7. Modular Structure. Score /5: 4.

Reason: Clean split into pure Rules, pure Render and IO-driving Kalah. A bare int[] board with static utility classes gives no encapsulation of board invariants.

Code quality principles. Item: 8. Problem Alignment. Score /5: 4.

Reason: Houses, stores, sowing, capture and scoring map directly to Kalah concepts. Players as 0 and 1 and the raw pit array are representation details rather than domain objects.

Test quality. Item: Test quality. Score /5: 4.

Reason: RulesTest pins sowing, store skipping, wraparound, every capture condition, turn passing, game over and scoring with clear names. RenderTest covers both directions and the 7-house layout. Unit tests mostly use only the 6-4 board, and the acceptance set leaves out a few variant/scenario pairs.
