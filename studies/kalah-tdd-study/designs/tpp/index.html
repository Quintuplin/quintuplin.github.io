How it builds code

The steps the agent followed, in order. Indented lines run under the line above them.

Family: Step size. Idea: Pick tests the simplest ranked transformation can pass. What it changes in the search: Move order. Cheapest transformation first.

once:1. Put Martin's ranked list with one-line definitions in the assistant prompt.repeat per feature until none is open:2. Pick the next test that the highest-ranked transformation can pass.3. Pass it with that one transformation. Name it in the commit message.4. Revert and try a simpler test if it needs while, function or assignment.5. Accept the lower-ranked move and log it if no simpler test exists.6. Refactor on green. Refactors change structure and never behaviour.7. Repeat until the test list is empty.

Once means one agent runs the steps. Repeat per unit means one agent per unit until no unit is open. Throughout means the rule joins every prompt. For up to n starts means separate attempts with the best kept. The harness does means the harness runs the step without an agent. If names the event that starts a stage, and with adds a rule borrowed from another method. Steps are quoted from args.json with their numbers. Tag: verified.

Review scores

A blind reviewer agent scored src/ and test/ from 1, worst, to 5, best, so the scores are unchecked. Reasons are the reviewer's own words, verbatim. This review is superseded by the blind rating of three raters in rating.json, whose medians fill the comparison's principle columns.

Review scores, 11 rows and 4 columns

Alterability. Item: Change Case 1: sow seeds anti-clockwise. Score /5: 5.

Reason: Sowing direction is handled only by mirroring the board in BoardView.lines, which is one if/else. Board and the game loop do not depend on direction at all.

Alterability. Item: Change Case 2: 7 houses with 5 seeds. Score /5: 3.

Reason: The house and seed counts go into the Board constructor in one place, and Board and cells scale with them. border and divider hardcode literal strings for 6 and 7 houses, so any other size would need new literals.

Code quality principles. Item: 1. Clear Presentation. Score /5: 4.

Reason: Formatting is tidy and the files are short and well ordered. The long BoardView.lines call in printBoard and the index arithmetic in sow are a little dense to read.

Code quality principles. Item: 2. Explanatory Language. Score /5: 4.

Reason: Doc comments explain intent, for example the mover's-lap pit indexing. Names like n, last and pit, and literals such as 2*n+1 and the 0/1 player ids, are only partly explained.

Code quality principles. Item: 3. Consistent Code. Score /5: 4.

Reason: Players are 0 and 1 throughout, and the static view helpers follow one style. Houses are numbered from 1 in the API but from 0 inside it, and some helpers are package-private for tests while their siblings are private.

Code quality principles. Item: 4. Used Content. Score /5: 5.

Reason: Every element is used. The starter placeholder was removed and nothing is dead.

Code quality principles. Item: 5. Simple Constructs. Score /5: 4.

Reason: The control flow is simple and the nesting is shallow. sow packs sowing, capture and the extra-move check into one method that uses modular arithmetic.

Code quality principles. Item: 6. Minimal Duplication. Score /5: 3.

Reason: border and divider each repeat near-identical literal strings for 6 and 7 houses where a loop could build them. play also repeats the Game over plus printBoard sequence on both exit paths.

Code quality principles. Item: 7. Modular Structure. Score /5: 5.

Reason: Board holds the rules, BoardView handles rendering and Kalah handles I/O and turns. Their dependencies are minimal and clean.

Code quality principles. Item: 8. Problem Alignment. Score /5: 4.

Reason: Board, sow, store, score and hasMoves match the domain language. Modelling direction as a pure rendering mirror is apt, but the code never states that this is why it works.

Test quality. Item: Test quality. Score /5: 4.

Reason: Many small, clearly named unit tests pin sowing, wrapping, skipping the opponent's store, captures, scoring and rendering, and spec tests cover each scenario end to end. The spec scenarios exercise only two of the four variants, anticlockwise 6-4 and clockwise 7-5.

## Summary

46 green commits used a median transformation rank of 6 (`unconditional->if`) and a mean of 6.07. 12 of 46 (26%) took a lower-ranked move of rank 10 or below, each logged with no simpler test available. There was 1 backtrack to a simpler test and 0 impasses across all 8 features.

Green commits are the behaviour commits that count as red-green cycles. Refactor, pinned-guard, tick and log commits are excluded. The 46 green commits match the 46 cycles in LOG.md.
