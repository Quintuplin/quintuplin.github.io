Review scores

A blind reviewer agent scored src/ and test/ from 1, worst, to 5, best, so the scores are unchecked. Reasons are the reviewer's own words, verbatim. This review is superseded by the blind rating of three raters in rating.json, whose medians fill the comparison's principle columns.

Review scores, 11 rows and 4 columns

Alterability. Item: Change Case 1: sow seeds anti-clockwise. Score /5: 5.

Reason: Sowing order is fixed in Ring and direction affects only drawing, so the clockwise flag reaches one predicate, BoardView.isLabelFirst, and Variant. Any combination with the 7-5 layout works without further changes.

Alterability. Item: Change Case 2: 7 houses with 5 seeds. Score /5: 5.

Reason: House and seed counts come from Variant.fromFlags and flow to Board, Ring, Score and BoardView as parameters. No rule code hard-codes 6 or 4.

Code quality principles. Item: 1. Clear Presentation. Score /5: 5.

Reason: Small files with consistent indentation and short methods. Each class opens with a one-line purpose comment and related methods sit together.

Code quality principles. Item: 2. Explanatory Language. Score /5: 4.

Reason: Names such as Ring, Capture, nextPit and isLabelFirst are descriptive and comments give rationale. Comments about keeping coupling at 5 record process more than intent, and null as a quit and tie signal stays implicit.

Code quality principles. Item: 3. Consistent Code. Score /5: 4.

Reason: Classes follow the same final, package-private, constructor-injection style. Board uses a static factory while siblings use constructors, and Ring and Score take houseCount separately where BoardView takes the Variant.

Code quality principles. Item: 4. Used Content. Score /5: 4.

Reason: Nearly everything is used. The House subclass adds nothing over Pit and Board.create only wraps a private constructor.

Code quality principles. Item: 5. Simple Constructs. Score /5: 4.

Reason: Control flow is flat with small loops. Ring relies on index arithmetic for opposite houses and own-house checks, and null return values signal quit and tie.

Code quality principles. Item: 6. Minimal Duplication. Score /5: 4.

Reason: Little repetition. Score.total and isSideEmpty repeat the same house loop, and Capture adds seeds one at a time in a loop instead of a bulk add.

Code quality principles. Item: 7. Modular Structure. Score /5: 5.

Reason: Responsibilities split cleanly across Board, Ring, Move, Capture, Turn, Game, Score, BoardView and Message with narrow dependencies. Kalah.play only wires the parts.

Code quality principles. Item: 8. Problem Alignment. Score /5: 5.

Reason: Classes map directly to domain terms such as house, store, pit, move, capture, turn and score. The variant concept is explicit in its own type.

Test quality. Item: Test quality. Score /5: 4.

Reason: Unit tests per class have clear behaviour names and independent setUp fixtures, and acceptance tests replay spec files for sowing, extra move, capture, tie and empty house. The 7-5 variant is pinned only by a quit-board test and Ring and Move tests cover the 6-4 layout only.
