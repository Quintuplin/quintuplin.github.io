How it builds code

The steps the agent followed, in order. Indented lines run under the line above them.

Family: Search and validation. Idea: Write the test that rules out the most wrong implementations. What it changes in the search: The check. Next test kills surviving mutants.

repeat per requirement until none is open:1. Finish one requirement with red-green-refactor cycles as usual.2. Run PIT or mutmut on the code that requirement touched.3. List surviving mutants. Set aside those no input could tell apart.4. Keep survivors that change an output a requirement names.5. Write the smallest requirement-level test that kills the most kept survivors.6. Take expected values from the requirement. Never from the current code's output.7. If the test fails on real code treat it as red and fix the code.8. Rerun mutation until no kept survivor remains. Then take the next requirement.

Once means one agent runs the steps. Repeat per unit means one agent per unit until no unit is open. Throughout means the rule joins every prompt. For up to n starts means separate attempts with the best kept. The harness does means the harness runs the step without an agent. If names the event that starts a stage, and with adds a rule borrowed from another method. Steps are quoted from args.json with their numbers. Tag: verified.

Review scores

A blind reviewer agent scored src/ and test/ from 1, worst, to 5, best, so the scores are unchecked. Reasons are the reviewer's own words, verbatim. This review is superseded by the blind rating of three raters in rating.json, whose medians fill the comparison's principle columns.

Review scores, 11 rows and 4 columns

Alterability. Item: Change Case 1: sow seeds anti-clockwise. Score /5: 5.

Reason: Direction is handled entirely as a rendering concern. BoardPrinter holds the only clockwise branch and the sowing model stays direction-agnostic, so any variant combination works without touching game logic.

Alterability. Item: Change Case 2: 7 houses with 5 seeds. Score /5: 5.

Reason: A single ternary in play() picks Board(7, 5) or Board(6, 4). Board and BoardPrinter derive everything from houseCount, so no other code changes.

Code quality principles. Item: 1. Clear Presentation. Score /5: 4.

Reason: Classes are short and well laid out with clear ordering. Kalah.java mixes the starter's tab-indented main with the new space-indented code.

Code quality principles. Item: 2. Explanatory Language. Score /5: 4.

Reason: Names like sow, captureAt, hasNoMoves and QUIT read well, and the Javadoc says why. P1 = 0 and the 1 - player idiom are clear, but houseCount() + 1 as the store position is explained only in a comment.

Code quality principles. Item: 3. Consistent Code. Score /5: 4.

Reason: The 1-based house API and the player constants are used the same way throughout. Indentation style is mixed in Kalah.java, and printResult is package-visible while its siblings are private.

Code quality principles. Item: 4. Used Content. Score /5: 5.

Reason: Every field, method and constant is used. No dead code or leftover stub output remains.

Code quality principles. Item: 5. Simple Constructs. Score /5: 4.

Reason: Loops are flat and short. The wrap condition in sow combines || and && without parentheses, which takes a careful read.

Code quality principles. Item: 6. Minimal Duplication. Score /5: 4.

Reason: Production code has no real repetition, and the houses helper serves both row directions. The board and transcript test helpers are copied across four test files.

Code quality principles. Item: 7. Modular Structure. Score /5: 5.

Reason: The split is clean. Board holds state and rules, BoardPrinter handles rendering and Kalah runs the IO loop, and each is package-private with minimal coupling.

Code quality principles. Item: 8. Problem Alignment. Score /5: 5.

Reason: Houses, stores, sowing, capture and score map directly onto the game vocabulary. Treating direction as a view of the same board matches the domain well.

Test quality. Item: Test quality. Score /5: 4.

Reason: The tests have clear names and pin sowing, the lap skipping the opponent's store, capture and no-capture, extra move, empty house, quit, game end, win and tie. Gameplay in the 7-5 variant and the anticlockwise 7-5 starting board are not exercised, and the helpers are duplicated across files.
