Review scores

A blind reviewer agent scored src/ and test/ from 1, worst, to 5, best, so the scores are unchecked. Reasons are the reviewer's own words, verbatim. This review is superseded by the blind rating of three raters in rating.json, whose medians fill the comparison's principle columns.

Review scores, 11 rows and 4 columns

Alterability. Item: Change Case 1: sow seeds anti-clockwise. Score /5: 5.

Reason: Direction is a pure view concern here: Board sows the same way in every variant and only BoardView's clockwise branch picks the row layout, so the change touches one small conditional.

Alterability. Item: Change Case 2: 7 houses with 5 seeds. Score /5: 5.

Reason: House count and seed count are constructor parameters used throughout Board and BoardView, so the variant is a single ternary in Kalah.play and all four combinations work without other edits.

Code quality principles. Item: 1. Clear Presentation. Score /5: 4.

Reason: The files are small and well formatted, with a clear order and related helpers next to each other. The sow loop's side/pit state is dense to scan.

Code quality principles. Item: 2. Explanatory Language. Score /5: 4.

Reason: Names and class Javadocs state intent well, and CANCELLED and the Protocol constants give literals meaning. The magic expressions 3 - side, 2 - player and player - 1 are never named.

Code quality principles. Item: 3. Consistent Code. Score /5: 4.

Reason: Players and houses are 1-based throughout and Protocol handles every message the same way. Opponent indexing switches between 3 - side and 2 - player, which is an inconsistent idiom.

Code quality principles. Item: 4. Used Content. Score /5: 5.

Reason: Every class, method and constant is used. The stub output was removed and nothing dead remains.

Code quality principles. Item: 5. Simple Constructs. Score /5: 3.

Reason: Game.run is a simple loop. Board.sow, though, encodes the last-seed-in-store case through the side flip and pit reset, and needs a comment to explain its return tests.

Code quality principles. Item: 6. Minimal Duplication. Score /5: 4.

Reason: Row rendering shares a houses helper with an ascending flag, and draw is factored out. Game over plus draw appears in two branches of run, and pit and pitEnd nearly duplicate each other.

Code quality principles. Item: 7. Modular Structure. Score /5: 5.

Reason: The responsibilities split cleanly into Board as the model, BoardView for rendering, Protocol for text and Game for the turn loop. Classes are package-private with narrow interfaces.

Code quality principles. Item: 8. Problem Alignment. Score /5: 4.

Reason: Board, house, store, sow and capture follow the domain vocabulary, and the variants map directly to constructor args and the view. The integer side/pit cursor is a lower-level encoding than the domain suggests.

Test quality. Item: Test quality. Score /5: 3.

Reason: BoardTest pins sowing, an extra turn, capture and scoring with clear names, and BoardViewTest covers two variant layouts. No own test exercises Game flow such as quit, empty house or end of game. ProtocolTest and PublicInterfaceTest mostly restate constants and signatures.
