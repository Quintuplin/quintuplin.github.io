How it builds code

The steps the agent followed, in order. Indented lines run under the line above them.

Family: Step size. Idea: One big step per feature. Drop a gear when it stalls. What it changes in the search: Step size. Large first then shrink on a stall.

throughout:2. Set four gears: feature, class, method, fake-it. Start in the feature gear.repeat per feature until none is open:1. Write one failing end-to-end acceptance test for the next feature.3. Attempt the whole feature in one assistant prompt against the acceptance test.4. Shrink rule: one failed attempt or 10 minutes red. Revert and drop a gear.5. In lower gears drive each class or method with its own unit test.6. Fake-it gear is classic TDD. Split any test still stuck there.7. Once acceptance passes add edge-case unit tests. Refactor on green.8. Return to the feature gear for the next feature.

Once means one agent runs the steps. Repeat per unit means one agent per unit until no unit is open. Throughout means the rule joins every prompt. For up to n starts means separate attempts with the best kept. The harness does means the harness runs the step without an agent. If names the event that starts a stage, and with adds a rule borrowed from another method. Steps are quoted from args.json with their numbers. Tag: verified.

Review scores

A blind reviewer agent scored src/ and test/ from 1, worst, to 5, best, so the scores are unchecked. Reasons are the reviewer's own words, verbatim. This review is superseded by the blind rating of three raters in rating.json, whose medians fill the comparison's principle columns.

Review scores, 11 rows and 4 columns

Alterability. Item: Change Case 1: sow seeds anti-clockwise. Score /5: 5.

Reason: Sowing logic is direction-neutral, and direction lives only in BoardRenderer's mirrored layout behind one boolean. Changing or adding a direction touches one small class.

Alterability. Item: Change Case 2: 7 houses with 5 seeds. Score /5: 5.

Reason: House and seed counts are constructor parameters of Board, chosen in one line of play(). The renderer and prompt derive everything from houseCount().

Code quality principles. Item: 1. Clear Presentation. Score /5: 4.

Reason: Classes and methods are short, consistently formatted and readable on one screen. The sow loop with its side/index/inStore flags takes some care to follow.

Code quality principles. Item: 2. Explanatory Language. Score /5: 4.

Reason: Names such as hasMoves, score, capture and gameOver match the domain, and the Javadoc explains the sowing rule. Players as raw 0/1 and the expression 1 - player are less explanatory than named constants.

Code quality principles. Item: 3. Consistent Code. Score /5: 4.

Reason: Style and idioms are uniform across the files. BoardRenderer defines P1/P2 constants while Board and Kalah use literal 0/1 and 1 - player.

Code quality principles. Item: 4. Used Content. Score /5: 5.

Reason: Every field, method and constant is used. The starter placeholder output was removed.

Code quality principles. Item: 5. Simple Constructs. Score /5: 4.

Reason: Plain arrays, loops and small helpers with no needless abstraction. The single sow loop that handles the store and side switching is a little dense.

Code quality principles. Item: 6. Minimal Duplication. Score /5: 4.

Reason: Rendering shares its houses/pad/border helpers between both layouts and the two-row board avoids mirrored logic. The two branches in render still repeat a similar line structure.

Code quality principles. Item: 7. Modular Structure. Score /5: 5.

Reason: Board holds the rules, BoardRenderer the output and Kalah the game loop and IO, each with one clear responsibility and narrow interfaces.

Code quality principles. Item: 8. Problem Alignment. Score /5: 5.

Reason: The code models houses, stores, sowing, capture, extra move and scoring directly in the game's terms. It recognises that the sowing direction is a matter of presentation.

Test quality. Item: Test quality. Score /5: 5.

Reason: BoardTest pins sowing, the store skip, laps, capture edge cases, extra move and scoring with clear independent names. Acceptance tests cover every scenario in all four variants plus a generated full-game end check for each variant.
