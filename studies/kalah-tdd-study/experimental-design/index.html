Study question

Classic greedy TDD writes the smallest failing test and then the smallest change that passes it. Do TDD variants that plan the class structure first, change the step size, try several starts or change how the tests check the code lead an AI coding agent to a better Kalah solution?

Run ended 2026-10-16. Model Claude Opus 5.5 (claude-opus-5-5). Runs: full-1 survey, tcp-1-list2 list reliability, rep-1 planned contrasts, rep-2 planned contrasts. 11 survey methods. Claims carry a tag. Recomputed means redone from source data. Verified means checked against a primary source. Unchecked means written or judged by an agent and not checked.

Task

The agent builds the course's Kalah assignment. The brief below is docs/SPEC.md at tdd-experiment c3dd988 verified.

Excerpt of the Assignment 2 brief ("Making Changes"), adapted for this experiment. The game rules and the output format are in README.md. Example specs are in examples/.

Task

Implement Kalah so that it supports all four variants below, and keep the implementation alterable. The variant is chosen by the two boolean parameters of play().

Restrictions

A significant amount of the assessment is based on an automatic marking system. If you ignore any of the following restrictions, your submission will not be marked.

  • No Java 9 (or later) features, including JDK. Java 8 is allowed.
  • No reference to any other files (e.g. use of configuration files).
  • No use of third-party libraries.
  • Do not use System.exit() under any circumstances.

The play() method

A test suite tests all variants together through this method:

    /**
     * Play a game of Kalah.
     * @param io Where to get input from and direct output to
     * @param clockwise If true, then sowing of seeds should be done in a clockwise direction,
     * otherwise if false sowing should be in an anti-clockwise direction.
     * @param sevenfive If true, then the game should have 7 houses per player, and start with 5 seeds in each house,
     * otherwise if false then it should have 6 houses per player starting with 4 seeds per house.
     */
    public void play(IO io, boolean clockwise, boolean sevenfive) {
      ....
    }

The Kalah.java stub runs the anti-clockwise 6-4 variant because of the parameters its main() passes to play(). To play another variant, change those values:

  public static void main(String[] args) {
      new Kalah().play(new MockIO(), false, false); // Change values of boolean parameters as needed
  }

So to change to the clockwise 6-4 variant, change the first parameter to true.

Variants

Your implementation must allow all 4 variants: 6 houses with 4 seeds both clockwise and anti-clockwise, and 7 houses with 5 seeds both clockwise and anti-clockwise. The specific variant being tested is given by how clockwise and sevenfive are set. The test cases are the same scenarios for each variant (4 sets of test cases). examples/EXAMPLES.md lists a sample of the test specifications.

Change cases

The implementation must allow all combinations of these two change cases.

Change Case 1: Sow seeds in an anti-clockwise direction

The game can be played with seeds sown in an anti-clockwise direction, the opposite of the clockwise sowing described in README.md.

Change Case 2: 7 houses with 5 seeds

The game can be played with 7 houses per player, each house starting with 5 seeds.

rep-2. State: complete. Tag: verified.

Course context

The COMPSCI 701 course items this study bears on.

Course context, 12 rows and 3 columns

Syllabus. Tag: verified.

Relevance: The course evaluates practices partly through research on their effectiveness. This study is a small empirical probe of TDD variants in that sense.

Lecture 11.2. Tag: verified.

Relevance: Calls TDD a development practice and a greedy algorithm for coding. It asks whether test order shapes the design and whether greedy design rules out good designs. Classic greedy TDD, its variants and the test-list order arms probe those questions.

Lecture 11.2 evidence. Tag: verified.

Relevance: Reports that TDD teams wrote smaller classes and methods with lower complexity and coupling and showed no clear cohesion trend. This page measures size but not complexity, coupling or cohesion.

Lecture 11.1. Tag: verified.

Relevance: Says design must be testable for TDD to work and defines testability as controllability and observability. No column of this page measures testability in that sense.

Lecture 2.1. Tag: verified.

Relevance: Splits maintainability into comprehensibility, alterability and testability. The rated cqp.html principles stand in for comprehensibility. Alterability is not measured here.

Lecture 2.3. Tag: verified.

Relevance: Defines a test case and a test criterion. The hidden, unseen and acceptance columns count passes of the course test suite. Mutation score is a test criterion stronger than the lecture's branch coverage example.

Lecture 7.1. Tag: verified.

Relevance: Measures alterability as classes changed over classes in the design against the impact of a change case. This study carries out no change case, so it computes no such ratio and leaves alterability unmeasured.

Lecture 1.2. Tag: verified.

Relevance: Applies noun and verb analysis to the Kalah description. Noun-verb map extends it with project rules from an A02 attempt, so those added rules are not course content.

Lecture 5.1. Tag: verified.

Relevance: Says many small functions can aid comprehension and that refactoring in several steps may first go backwards. Functions first, classes later and Annealed refactoring probe those two points.

Lecture 4.1. Tag: verified.

Relevance: Stresses that metric thresholds give false positives and false negatives. Strict PMD compliance reports conformance to the course ruleset and alone does not show maintainability.

A02 rubric. Tag: verified.

Relevance: Functionality is 15 of 20 marks and maps to Functional mark /15. The 5 report marks are not scored here. The assignment judges alterability from a change actually made. This study builds all four variants at once and does not measure alterability.

A01 rubric. Tag: recomputed.

Relevance: Used the course PMD ruleset for maintainability marks and asks for at least 4 classes besides Kalah and enums. Seven of the 11 methods have 4 classes or fewer in total with Kalah included.
