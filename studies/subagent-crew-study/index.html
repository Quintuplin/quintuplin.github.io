A subagent crew for coding agents

Development and evaluation of a five-role delegation pipeline for Claude Code. The primary evidence is a controlled effort comparison study on tasks drawn from the history of a real team-built mobile app.

Summary

The crew at high effort shipped the fewest defective changes of six setups and sits on the correctness frontier. It costs less than max effort solo and less than ultracode. It costs about three times a solo agent at the same effort, so on cost alone a solo agent at high effort is the better buy.

The crew

A main session talks to the developer and delegates each code change to five subagents in a fixed order. Each subagent runs in its own context with its own model and tool permissions. Only the implementer may write files. The reviewer reads the diff and cannot edit it. The main session keeps every outward step such as pushing, opening the pull request and deploy decisions. Merging stays with the developer.

Opus model Sonnet model main session light tier path failure path

The workflow is called RPD for Requirements, Plan and Deliver. Small diffs in one package take a light tier that skips the reviewer. Review fix rounds are capped at three before the developer decides. Every bug fix must ship with a regression test that CI runs.

Agent design framing

A common way to classify model use separates a one-shot prompt, a fixed workflow and an agent. The crew is a hybrid. Its stage order is a fixed workflow written in rules. Each stage is a full agent that runs the perceive, reason, act and observe loop with tools. Current agentic coding tools share the same building blocks this crew uses.

Agent conceptIn the crew
Plan-then-executeThe architect writes a noun-verb plan. The implementer executes it in numbered groups.
ReflectionThe reviewer critiques each diff. Must-fix findings go back to the implementer for at most three rounds.
SubagentsFive roles, each with its own context and model. The parent keeps control of every outward action.
PermissionsAllow, ask and deny per role. The reviewer and explorer cannot edit. A push that deploys needs explicit approval.
Instruction fileA shared rules file such as AGENTS.md or CLAUDE.md read at every session start. Instructions, not memory.
Tests as ground truthThe verifier runs local checks pinned to the CI toolchain. CI must start before the turn ends.
Delegation has a budgetEach subagent re-reads context and tokens multiply. The study below measures that cost directly.

Ultracode is the comparison setup. It lets a single agent write an orchestration script at run time that fans work out to many subagents. In these terms the agent builds its own fixed workflow per task. The crew fixes the workflow once in advance.

A common rule of thumb says an agent earns its cost when the steps are unknown in advance. The study asks the same question one level up. Does a pipeline of agents earn its cost over one agent?

Study design

The effort comparison study is a controlled benchmark with a pre-registered analysis plan. Every setup used the same model, Claude Opus 5.5, on the same tasks in a sandbox with no network access. Setups differ only in reasoning effort and in whether the crew or ultracode is switched on.

Tasks from a real project history

The source project is a location-based mobile app. It is a Flutter app in the MVVM pattern with a Node back end on PostgreSQL and PostGIS, built by a five-member student team. Its git history supplied realistic tasks. The study read it through a one-time static import and never touched the live repository.

Controls and measures

  • Each run starts in a fresh sandbox with no network egress. Runs that broke the sandbox are left out. verified
  • Resolution is the hidden tests passing on the agent's committed diff. Unresolved runs count as failures. verified
  • Defects come from a blinded review of each shipped diff after the runs ended. verified
  • Cost is API-equivalent USD per task. Time is wall minutes per task without API retry waits. verified
  • A budget guard started no new run while either usage window stood at or above 60%. verified

Analysis plan

  • Friedman test across the registered family, then paired Wilcoxon tests with Holm correction. verified
  • Hodges-Lehmann shifts with a bootstrap over tasks for confidence intervals. Cochran's Q for resolution. verified
  • Cost ratios are geometric means of per-task ratios. verified
  • Sample size was fixed in advance with no interim look. With 12 tasks the paired design detects an effect of about dz 0.81. verified

Stage full ran 84 runs across A, B and C. Stage full-med ran 56 runs across D and E. Stage full-ultra ran 14 runs of F. API-equivalent spend was about $1,170 in total. verified

Critical questions

Does the crew raise correctness?

direction only

High crew shipped 0 defective diffs of 18 and had the lowest failure or error rate. No pairwise difference reaches significance. One extra defect could reorder the setups. recomputed

Is the crew cheaper than raising solo effort?

supported

This is the pre-registered primary comparison. High crew costs 0.77 times max solo at Holm p 0.003 and resolves 18 of 20 runs against 17 of 21. recomputed

Does the crew pay for itself against a solo agent at the same effort?

answered no on cost

High crew costs 3.34 times high solo and takes about 3.6 times as long. High solo resolves a larger share and has the best effect per dollar. The crew buys fewer leftover defects for that price. recomputed

Is the crew better value than ultracode?

open

High crew costs $4.94 less per task at equal effect and a lower failure or error rate. The cost ratio is not significant at Holm p 0.107 with one ultracode repetition per task. recomputed

Does the crew help at medium effort?

answered no

Medium crew costs more than high solo and resolves a smaller share of runs. Its failure or error rate is the highest of six setups. recomputed

Do the results generalise beyond this benchmark?

open

The tasks are small entry tasks from one project. The rule of thumb predicts agents earn their cost when steps are unknown in advance. Larger tasks with unclear steps may favour the crew more. This study does not test that. unchecked

Limits

  • Every figure on this page uses one basis. That is gate-passing runs on the 11 tasks complete in every setup. Task 356 leaves because one setup has no valid run there. One max solo run fails the reconcile gate. Three runs with a sandbox violation are left out. recomputed
  • The error rate grade and the ultracode pairing rule were set after results were seen. Treat both as exploratory. verified
  • Ultracode ran one repetition per task due to cost. The other setups ran two. verified
  • A defect count of 0 is a lower bound. The rule of three puts the upper 95% bound for high crew near 0.17. recomputed
  • One model, one project and 11 analysed tasks. The same person designed the crew and the benchmark. Hidden tests and blinded defect review reduce that bias but do not remove it. verified
